## §0 導讀：這是什麼開發環境

這不是「裝了幾個 Claude Code 外掛」，而是一套**讓 AI 開發代理具備長期記憶、結構化檢索、
規範自動執行、以及從自身行為中學習**的完整環境。核心設計理念是：

> **人不該重複告訴 AI 同一件事。**
> 說過的話存進 DB、犯過的錯記成違規熱區、學會的模式沉澱為直覺、能力封裝成 Skill —— 全部自動回注下一次對話。

六大子系統各司其職，彼此以 SQLite 為交會點：


| 子系統            | 一句話定位    | 核心載體                                                      | 「不裝會怎樣」                   |
| ------------------- | --------------- | --------------------------------------------------------------- | ---------------------------------- |
| **A. 知識與記憶** | AI 的長期記憶 | `.context-db/phycool.db`（55 表）                             | 每開新視窗都要重講一次專案背景   |
| **B. 檢索三引擎** | AI 的眼睛     | CodeGraph / GitNexus / RAG 12 層                              | 靠 grep 摸索，改東壞西           |
| **C. 規範執行**   | AI 的紀律     | 41 Rules + 67 Hook 掛載點                                     | 規範寫在文件裡沒人遵守           |
| **D. 能力封裝**   | AI 的技能樹   | 125 Skill + 81 Command + 10 Agent                             | 每次都要在 prompt 裡貼一長串規格 |
| **E. 工作流**     | AI 的作業程序 | BMAD 4 模組 + Pipeline 子視窗                                 | 開發流程靠人腦記，品質不穩       |
| **F. 自我演化**   | AI 的直覺     | ECC 6 表 + 湧現閘門 + 5 支自動作業（收割失敗／**收割人類糾正**／衰減／量測／stale）+ **Gemini 常駐 agent（shadow，2026-08-15）** | 同樣的坑踩無數次                 |

**打包定位**：A / B / C / F 為**通用機制**（🟢 可直接開源）；D 需分級（🟡 業務知識剔除）；
E 的 BMAD 本體需使用者自行安裝新版，客製化覆蓋層才是本包內容。

> **上表數字是「本開發環境的規模」，不等於「開源包的內容」。**
> 開源包依業務內容禁入原則剔除產品資訊後為 **1,482 檔**：
> rules 40（扣業務專屬 1 條）· hooks 56 · **settings.json.template（67 掛載點）** ·
> skills 49 個（扣 5 個業務綁定 Skill + 業務 `phycool-*` + `generated/`）·
> commands 13（BMAD 68 需自行安裝本體）· agents 10 · context-db 204 · dev-console 267 ·
> party-to-pipeline 20 · scripts 40 · bmad-overlay 73。
> 完整清單與剔除理由見 [09 打包與部署](開發環境架構清單/09-打包與部署.md) §9.2。

### 裝到別台機器

範本中的路徑是 `${PROJECT_ROOT}` / `${USER_HOME}` / `${PROJECT_SLUG}` 佔位，
**不要手動複製 `config-templates/`** —— 佔位不會自己變成你的路徑，
`settings.json` 的 hook 指令會是字面的 `cd "${PROJECT_ROOT}"`，67 個掛載點全數失效。

```powershell
node scripts/install-devenv.cjs --project-root "D:/Work/my-project"          # 預覽
node scripts/install-devenv.cjs --project-root "D:/Work/my-project" --apply  # 安裝
```

端到端實測（2026-08-08）：還原 1,362 檔，67 個掛載點引用的檔案全部到位，
0 殘留佔位、0 殘留原專案路徑。後續步驟見 09 章 §10。

## §1 系統全景與資料流

### 1.1 一次對話的完整旅程

```
使用者輸入 prompt
   │
   ├─[UserPromptSubmit ×5 hooks]────────────────────────────────┐
   │   pre-prompt-rag.js       → 12 層 RAG 注入（見 §3.2）      │
   │   bmad-slash-story-inject → 偵測 /bmad 指令補 Story 上下文  │
   │   ctrl-channel-inject     → 跨軌未讀訊息注入               │
   │   worker-notify-inject    → 子視窗完成通知                 │
   │   tianji-reject-cooldown  → 外部方案冷卻期檢查             │
   │                                                             │
   │   同時：INSERT INTO conversation_turns（role=user）★        │
   └─────────────────────────────────────────────────────────────┘
   │
   ▼  AI 開始工作
   │
   ├─[PreToolUse ×20 hooks]  工具執行前攔截
   │   config-protection · read-before-edit-guard · encoding-bom-guard
   │   cross-ref-precheck · skill-tool-invocation-guard · file-lock-check
   │   → 違規則 BLOCK 並回饋原因（見 §4.2）
   │
   ├─[工具執行]  Read / Edit / Write / Bash / MCP...
   │
   ├─[PostToolUse ×14 hooks]  工具執行後記錄
   │   observe-pattern.js      → 行為觀察入 pattern_observations ★
   │   db-first-write-guard    → 攔截 Story .md 鏡像
   │   skill-index-drift-detector · report-paradigm-guard
   │   file-lock-acquire       → 檔案鎖登記
   │
   ▼  AI 回應完成
   │
   └─[Stop ×12 hooks]
       log-session.js          → 快照入 conversation_sessions/turns ★
       incremental-embed.js    → 新內容向量化 ★
       debt-discovery.js       → 掃出技術債入 tech_debt_items
       detect-rule-violation   → 違規偵測入 context_entries ★
       ecc-emergence-gate.cjs  → 直覺湧現閘門 ★
       suggest-compact         → context 用量建議
       stop-report.ps1         → Pipeline 子視窗回報
       ceo-briefing-generator  → 決策簡報生成
```

★ 標記處 = 寫回 DB，構成下一次對話的注入素材（閉環起點）。

### 1.2 資料匯流點

```
                    ┌──────────────────────────┐
   Claude Code ────▶│                          │◀──── DevConsole Web UI
   Hooks (67)       │  .context-db/phycool.db  │      (22 頁面 / 25 API)
                    │      55 實體表           │
   MCP Server ─────▶│      14 FTS5 全文索引    │◀──── CLI 腳本 (149 支)
   (36 tools)       │      138 索引            │
                    └──────────────────────────┘
                        ▲            ▲
       符號 / 文檔向量   │            │  視窗存活 / 停滯 / 催辦旗標
          ┌─────────────┴──┐         └──── pipeline-guardian.ps1
    CodeGraph        GitNexus              （常駐守護單例，住在所有
  (59,750 nodes)  (95,398 nodes)             子視窗外面 · 見 06 章 §6.3.2）
```

> 上圖三個寫入來源的差異值得注意：hooks 與 MCP 是**對話驅動**（有人在講話才會寫），
> CLI 腳本是**手動驅動**，而守護迴圈是**唯一的常駐背景寫入者** —— 沒有任何對話發生時它仍在寫，
> 這正是它能回答「子視窗死了沒人知道」的原因。

## §8 六條核心閉環總覽


| # | 閉環              | 起點          | 沉澱處                                                                         | 回注點                           | 對應章節 |
| --: | ------------------- | --------------- | -------------------------------------------------------------------------------- | ---------------------------------- | ---------- |
| 1 | **對話記憶**      | 使用者 prompt | `conversation_sessions/turns/embeddings`                                       | Layer 1 +`search_conversations`  | §2.4    |
| 2 | **檢索索引**      | code 變更     | `symbol_index` / `god_nodes` / embeddings                                      | Layer 4 (S_final 融合)           | §3.3    |
| 3 | **違規學習**      | AI 違反 rule  | `context_entries`(rule_violation)                                              | Layer 11 違規熱區                | §4.3    |
| 4 | **Story 治理**    | 需求          | `stories` / `review_findings` / `tech_debt_items`                              | `search_stories` 查重 + Layer 3  | §6.2    |
| 5 | **Pipeline 握手** | 中控派發      | `worker_runs`（9 態 lifecycle）                                                | `worker-notify-inject` + Layer 7 | §6.3.1  |
| 6 | **ECC 演化**      | AI 行為       | `pattern_observations` → `instincts`（+ `injection-log` / `efficacy-latest` / `agent-precompute`） | Layer 12 直覺注入（agent 消費 shadow） | §7.2    |

**共同特徵**：每條閉環都是「行為 → 記錄 → 沉澱 → 自動回注」，**不依賴人記得去查**。
這是本環境與「裝了一堆工具」的根本差異。

**第 5 條的特殊性 —— 唯一需要「旁路觀測者」的閉環**：其餘五條的起點都是**對話中發生的事件**
（prompt / code 變更 / 違規 / 需求 / AI 行為），有人在講話就一定會被 hook 攔到。
但 Pipeline 握手的起點在**另一個進程**：中控派發後，薄手隨即退出，中控與 worker 之間沒有同步連線 ——
worker 死掉、回報沒人收、卡住不動，這三件事**不會產生任何對話事件**，沒有 hook 會被觸發。
因此本閉環額外掛了一條旁路：`pipeline-guardian.ps1` 常駐守護（06 章 §6.3.2），
以 30s/600s 雙節奏在對話之外持續觀測，把結果寫成 `worker_runs` 旗標，
再由 `worker-notify-inject` 於中控下次 prompt 時注入 —— 補回那條斷掉的回注路徑。

> 守護只寫旗標，**零終止原語、絕不關窗**。關窗有且僅有兩條合法途徑：
> **握手裁定 `approved` 後由派發方中控呼叫 `close-worker.ps1`**，或使用者手動關閉。詳 06 章 §6.3.1。
>
> **（2026-08-11）該腳本內另有第二階段 `-Reap`**：第一階段送出 taskkill 後若視窗在確認窗內仍存活（`WHP6-E06`），
> 由於它採「**先寫終態、後殺行程**」，DB 此刻已是 `lifecycle='closed'`，該 run 便**永久**過不了第一階段的
> `approved` 前置 —— 亦即 **E06 不是「重試一次就好」，而是使該 run 在正規途徑上失去關窗能力**，
> 這正是先前「每張卡都要人工關窗」的結構性原因。`-Reap` 是開在**同一條授權途徑之內**的窄門（不是另闢途徑）：
> 入場條件為第一階段留下的特徵組合（`closed` + `requires_attention=1` + `close_source` 可收屍），
> 握手證據逐項沿用不放寬，判活仍複用同一個 `judgeLiveness()`，差別只在**手段升級**
> （第一階段刻意只下一次 taskkill 不 fallback；第二階段追加 `Stop-Process -Force`，
> 因為第一階段那次 taskkill 已對這個 PID 證明無效，重試同一招沒有理由會成功）。
> 狀態上 `closed_at`（第一階段）與 `closed_detected_at`（第二階段）之差即**殘留視窗實際存活時長**。
