## 1. 可觀測性（OpenTelemetry 微型收集器）

### 1.1 架構與實測數據

| 項目 | 內容 | 實測驗證 |
|------|------|----------|
| **收集器** | `scripts/otel-micro-collector.js` — 本機輕量 OTel collector | ✅ 運行中 |
| **Port 策略** | **動態配埠 49152–65535**，實際埠寫入 port file；`--port` 可指定固定埠 | `otel-micro-collector.js` L20 / L117 `PORT_MIN` / L311 `FIXED_PORT \|\| randomPort()` |
| **啟動 Hook** | `scripts/otel-auto-start.js` (SessionStart hook，冪等) | ✅ 掛載驗證 |
| **彙總 Hook** | `scripts/otel-session-aggregate.js` (SessionEnd hook，glob-resilient) | ✅ 掛載驗證 |
| **主視窗啟動** | `scripts/start-main-otel.ps1` | ✅ 可手動觸發 |
| **Skill** | `phycool-otel-micro-collector` (含 rotation 設計) | ✅ 存在 |
| **用途** | 追蹤各 workflow 的 token 消耗、耗時、失敗率，寫入 `workflow_executions` (1,050 筆) | ✅ DB 確認 |

### 1.2 OTel Collector 實作細節 (`otel-micro-collector.js`)

```javascript
// 接收端點: http://localhost:<實際埠>/v1/traces / /v1/metrics / /v1/logs
// 協定: OTLP HTTP/JSON
// 儲存: 寫入 workflow_executions 表 (via MCP log_workflow 或直接 DB)
// Rotation: 按日期/工作流類型分檔，防單檔過大
// 配埠: BR-001 動態 port (49152–65535) + port file 寫入機制；
//       每個 worker 各自取埠，避免多視窗互搶。要固定埠需顯式帶 --port
```

> ⚠ **2026-08-08 覆核修正**：本節 v3.1.0 曾記「實測 Port 49152 / 主視窗固定 port 49152」。
> 實際 `49152` 是 `PORT_MIN` 常數（IANA 動態埠範圍下界），**不是固定埠**。
> 該版同時指出 `.claude/rules/context-memory.md` 記載的 49200 為舊值 —— 方向正確
> （49200 確實不在程式碼中），但把 `PORT_MIN` 讀成實測埠是新的誤讀。
> 驗證埠號請讀 port file 或查 process，不要假設任何固定值。

### 1.3 驗證指令

```bash

netstat -ano | findstr LISTENING | findstr node

# 2. Collector 健康檢查（<port> 代入上一步取得的實際埠）
```

### 2.2 預算分配驗算 (bwu-11/bwu-14 收斂後)

```
Layer 1  Session:           2,400 chars
Layer 2  Tech Debt:           (併入 L3)
Layer 3  Task Aware:            550 chars (bwu-11 新增)
Layer 4  Code RAG:            1,450 chars
Layer 5  Doc RAG:               650 chars
Layer 6  History Decisions:     (併入 L3)
Layer 7  Pipeline State:        300 chars (bwu-11 新增)
Layer 8  Skill Rec:             400 chars (bwu-11 新增)
Layer 9  LSP Diag:              750 chars
Layer 10 IDD:                 1,400 chars
Layer 11 Violation:             650 chars (cascade 5→3→1)
Layer 12 Instinct:              450 chars (inject-budget.cjs 定義)
Layer 13 godNodes:              118 chars (固定 advisory)
───────────────────────────────────────
總計:                        9,118 chars ≤ MAX_INJECT_CHARS(9,500)
預留緩衝:                       382 chars (吸收 formatter 截斷溢出)
降級告警預留:                   600 chars (DEGRADE_NOTICE_RESERVE)
```

> ⚠ 2026-08-08 覆核修正：原記「總計 9,280 / 預留 220」與逐列相加不符，
> 且與本章 §8.6 的驗算腳本（同一組常數）結果矛盾。逐列相加實為 **9,118**。

> **關鍵修正** (bwu-11/bwu-14)：修前全部預算以 token 計 (MAX_TOKENS=10000 搭配 estimateTokens=length/4)，換算後實際放行約 40,000 字元 = 官方上限 4 倍。現已全面改以**字元**為單位，與官方 10,000 字元硬界同量綱。

|------|------|--------|------|

### 4.2 鎖結構與識別

```json
// .agent-locks.json 範例
{
  "src/YourApp/Web/Services/SomeService.cs": {
    "holder": "CC-OPUS",
    "acquired_at": "2026-08-07T15:30:00+08:00",
    "operation": "Edit"
  }
}
```

- 鎖以 `-AgentId` 識別持有者 (如 `CC-OPUS`)，對應 `CLAUDE.local.md` 的引擎身分矩陣
- 多視窗並行時防止兩邊改同一個檔

### 4.3 驗證指令

## 5. Worktree 並行隔離

### 5.1 實測規格

| 項目 | 內容 |
|------|------|
| **位置** | `.claude/worktrees/` (`.gitignore` L81 排除) |
| **Skill** | `worktree-manager` |
| **Pipeline 整合** | `dispatch-general.ps1 -Worktree` — 子視窗在獨立 git worktree 執行 |
| **建立成本** | 約 200-500ms + 磁碟空間 |
| **清理** | 未變更時自動移除 |
| **速查** | `worktree-quick-reference.md` |

### 5.2 運作流程

```
dispatch-general.ps1 -Worktree
    │
    ├─ git worktree add .claude/worktrees/{runId} -b pipeline/{runId} HEAD
    │
    ├─ 啟動新 Claude Code 視窗 (cwd = worktree 路徑)
    │
    ├─ Worker 執行 (獨立 git 狀態，不影響主 worktree)
    │
    ├─ 完成後 close-worker.ps1
    │     ├─ 關閉視窗
    │     ├─ git worktree remove .claude/worktrees/{runId}
    │     └─ (若有變更) 中控決定合併策略
    │
    └─ 主 worktree 保持乾淨
```
