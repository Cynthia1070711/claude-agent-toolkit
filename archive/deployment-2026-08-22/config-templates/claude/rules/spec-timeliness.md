# Spec Document Timeliness

## 核心原則：程式碼永遠是真實狀態

引用功能規格文檔時，必須交叉驗證程式碼，不可盲信規格描述。

## 時效性判斷優先級（由高到低）

1. **程式碼**（components/、services/）— 永遠是當前真實狀態
2. **UI/UX 規範/** — UI/UX 改版在此更新，通常比功能規格新
3. **functional-specs/** — 初始需求定義，可能落後於實作

## 強制規則

1. **引用前比對時間戳**：檢查規格的「最後審閱」日期 vs 程式碼的 @date/@changelog，較新者為準
2. **衝突時以程式碼為準**：發現規格 vs 程式碼不一致，以程式碼為準，並標記規格需更新
3. **UI/UX 議題先讀程式碼**：討論任何 UI 相關議題前，先讀實際組件程式碼確認當前狀態
4. **多版本文件取最新**：同一主題有多份文件時，以時間戳最新者為準
